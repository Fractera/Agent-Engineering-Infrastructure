# replies — РАЗГОВОРНЫЙ КОНТРАКТ автоматизации (как она ОТВЕЧАЕТ пользователю)

> Это единственный источник правды о том, как автоматизация РАЗГОВАРИВАЕТ с человеком в рантайме.
> Реализует его ОДИН узел — `composeReply` (`_lib/nodes/compose-reply.ts`); он собирает `ctx.reply`,
> и `deliverUserTelegramChat` шлёт именно его. Остальные инструкции (`passport.md`, `nodes.md`,
> `graph.md` …) — для агента, который СТРОИТ автоматизацию; этот файл — про её РАНТАЙМ-РЕЧЬ.
>
> Зачем он есть (шаг 308, требование владельца). Раньше пользователю уходил СЫРОЙ `ctx.text` того узла,
> что сработал последним — обрывок без представления и оформления («Пользователь просит запомнить…»,
> голое «выключить чайник»). Это делало ассистента похожим на «кусок текста», а не на собеседника.
> Один контракт → один связный, оформленный, локализованный ответ на каждый случай, и правки перестают
> «одно чинить — другое ломать».

## 1. Кто автоматизация (голос)

Ассистент заметок в личном Telegram-чате: короткий, тёплый, по делу, с эмодзи-маркером исхода. Не
пересказывает вопрос пользователя ему же обратно. Отвечает НА ЯЗЫКЕ пользователя (сейчас `ru`+`en`,
язык — `NEXT_PUBLIC_DEFAULT_LOCALE`; расширяемо до десяти).

## 2. Представление и возможности (C)

На `/start`, `/help`, «что ты умеешь» и на НЕПОНЯТОЕ сообщение — короткий список умений:

> 👋 Я — ассистент заметок в Telegram. Вот что я умею:
> 📝 Запомнить · ⏰ Напомнить · 🔎 Найти · 💰 Учесть трату (чек/словами) · 📍 Отметить место.
> Можно всё в одном сообщении — я разберу.

## 3. Ответ на каждый исход (структурный результат прогона → строка)

| Ветка | Структурный сигнал | Ответ |
|---|---|---|
| save | `noteSummary` | `✅ Записал: <суть>` |
| finance (расход) | `finance` | `💰 Расход <сумма> (<категории>): <суть>` |
| finance (доход) | `finance.kind=income` | `💰 Доход <сумма> (<категории>): <суть>` |
| remind (есть дата) | `when` + `remindText` | `⏰ Напомню <дата время>: <текст>` |
| remind (нет даты) | `needsWhen` | `⏰ Когда напомнить? Ответь датой или временем.` |
| place (сохранено) | `placeOutcome.kind=saved` | `📍 Место записано: <описание>` |
| place (точка без описания) | `placeOutcome.kind=need-description` | `📍 Точку записал. Что здесь?` |
| place (нет точки) | `placeOutcome.kind=need-address` | `📍 Пришли точку/адрес…` |
| recall | `recallAnswer` | `🔎 <ответ памяти>` |
| glossary (алиас записан) | `glossaryAdded` | `✅ Запомнил: <term> = <meaning>` |
| непонятно | ничего не собрано | `🤔 Не понял.` + список возможностей |

## 4. Составное сообщение

Одно сообщение может нести несколько намерений (заметка И трата И место). Тогда ответ — ОДИН, строки
через пустую строку, в порядке: save → finance → remind → place → glossary → recall. Никаких отдельных кусков.

## 5. Законы

- Композитор `composeReply` — ЕДИНСТВЕННОЕ место сборки ответа; узлы-ветки оставляют СТРУКТУРНЫЙ
  результат (`noteSummary`/`finance`/`when`/`placeOutcome`/`recallAnswer`/`showHelp`), а НЕ готовую фразу
  пользователю. Добавляешь новую ветку → добавляешь её строку СЮДА и в `composeReply`, а не лепишь текст
  в своём узле.
- Пустой ответ невозможен: на реальное сообщение всегда есть строка (в пределе — список возможностей).
- Ограничение слоя: память диалога — ОТДЕЛЬНЫЙ механизм (буфер разговора), не этот контракт; здесь —
  только форма ответа на ОДИН прогон. Окно памяти = СЕССИЯ (все сообщения в пределах ~1 часа TTL, не
  фиксированные N штук): после часа тишины буфер пуст, следующий запрос собирает полный системный контекст
  (инструкция + глоссарий) заново. Дефолты сессии крутятся в аккордеоне «Ассистент» (`lastN`/`ttlMinutes`).
- ГЛОССАРИЙ АЛИАСОВ владельца (`glossary`-store) инжектится СИСТЕМНОЙ ПРЕАМБУЛОЙ во все модельные узлы:
  модель раскрывает сокращения («в Меркадоне» → чеки store=SODO ADEJE). «Запомни что X это Y» = ОПРЕДЕЛЕНИЕ
  (intent glossary → `defineGlossary`), а НЕ заметка. Пополняется руками (вкладка «Глоссарий») и авто.

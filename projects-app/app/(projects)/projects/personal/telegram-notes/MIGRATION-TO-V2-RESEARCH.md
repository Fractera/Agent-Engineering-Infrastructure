# Telegram Notes как эталон приёмки v2: дорожная карта дозревания второй версии

> Дев-сессионный документ. Рамка (уточнена владельцем): telegram-notes v1 — доказанный **прототип**, чья
> архитектура НЕ масштабируется; ради масштаба начата v2. То, что v2 пока не умеет части telegram-notes, —
> **не приговор переносу, а техзадание на дозревание v2**. Разрывы = backlog развития. Этот файл описывает
> различие архитектур, метод и **план доработки v2** до планки telegram-notes. Источники прочитаны живьём:
> v1 (`personal/telegram-notes`) и замороженный v2-шаблон (`_lib/starters/stream/en`).

---

## 1. Главное: telegram-notes — это спецификация зрелости v2

v1 доказал набор способностей. v2 обязана вырасти так, чтобы выразить их НАТИВНО (в своих терминах: ядро
`automation.json`, движок `_lib/executor.ts`, закрытый словарь каналов, механизм `capability`). Когда группа
автоматизаций telegram-notes соберётся и пройдёт живой прогон в v2 — v2 дозрела до этой планки.

**Важнейшее открытие:** v2 УЖЕ предвидела эти разрывы. Механизм `capability` (схема §CAPABILITY) описывает
узел, чья функция не пишется своим кодом, а тянется к внешнему инструменту (MCP/навык/API), статусами
`needed → candidate → bound → proven`. Наши разрывы — это способности в статусе `needed`. Дозревание v2 =
довести конкретные способности до `bound/proven` + несколько маленьких аддитивных транспортов. Ничего в
архитектуре ломать не нужно.

## 2. Различие архитектур (корень, а не перечисление)

### v1 (не масштабируется)
- Источник истины — машинный блок `<!-- fractera:project … -->` в `README.md`; из него ГЕНЕРИРУЮТСЯ
  `_data/flow.ts`, `_data/actions.ts`, durable-воркфлоу `_workflow/definition.ts` (WDK).
- Исполнение — durable Workflow DevKit; узлы `trigger`/`step`/`router`, ветвление по `actions`.
- Единица — **Action** (save/remind/recall) с hook-фразами (шаг 187, глобальная таблица `project_hooks`).
- Свободно тянет платформу: `@/lib/db`, `@/lib/rag`, `@/lib/hooks/normalize`.

### v2 (масштабируемая, но сырая)
- Источник истины — `_data/automation.json`, только через `load.ts` (Zod). Правка — `api/patch`.
- Исполнение — собственный `_lib/executor.ts`: топо-обход **видимых** узлов, общий context-bag,
  узел = `(ctx) => частичный ctx`, первый throw останавливает, `null` из условия = штатная остановка.
- Единица — **Message** (`_lib/message.ts`): один контракт данных на все каналы. «Захват → развозка»,
  линейно. Общий контракт делает канал СМЕННЫМ.
- Граф — три группы (`input`/`middle`/`output`), `cuid`+`state`, каналы `ioType` = **закрытый словарь**,
  связи из `KIND_PORTS`. Рождается с полным инвентарём дверей, всё скрыто; строитель раскрывает.
- Виды: вход `input`/`input-connector`; середина `transform`/`condition-success`/`condition-failure`;
  выход `output`/`output-connector`. Роутера на N ветвей нет — **осознанное решение**, не пробел.
- **`capability`** — узел вправе объявить нужду во внешнем инструменте (механизм для AI/памяти/дат).
- **Самодостаточность (закон 0/1):** рантайм зависит только от `zod` + node-builtins, уезжает ZIP'ом.
  Вся v1-логика на `@/lib/*` пере-выражается через `_lib/rows.ts`, `_lib/memory.ts`, `api/env`.

### Что именно telegram-notes требует от незрелой v2
| Способность v1 | Статус в v2 сегодня | Что это в терминах v2 |
|---|---|---|
| Сводка сообщения (дешёвая модель) | не построено | `capability` AI на `transform` (есть `passport.ai` + `api/ai-models`, но ни один узел не зовёт модель) |
| Запись факта в память | **готово** (`rememberFact`) | канал `vector-memory` |
| **Recall** — поиск по памяти и ответ | **отсутствует** | память только на запись; нужен `recallFacts(query)` + `transform`-чтение |
| **Reminder** — дата из текста + доставка по наступлению в личный чат | частично | `api/calendar-tick`+`deliverDue` есть, но без канала `user-telegram-chat` и без разбора даты |
| Роутинг 3 действий по hook-фразам | по-другому | закон v2: разные сценарии = **группа автоматизаций**, каждая сама-гейтит свою фразу |

## 3. Метод (как правильно строить план дозревания)
1. **Каждый разрыв — это способность, а не «доработка кода».** Формулировать в машинерии v2: либо
   `capability: needed→bound`, либо аддитивный транспорт, либо конвенция моделирования. Не тянуть v1-паттерн
   (закон 3: молчание = запрет).
2. **Разрыв способности — паузой-warning владельцу, не тихой заглушкой** (память
   `feedback-capability-user-supplies-tool`): платформа предсказывает «узел должен делать 123 → нужен
   инструмент», владелец отвечает в `reply`.
3. **Один сценарий = одна автоматизация.** save/remind/recall = группа. N-веток внутри одной не выражается и
   не должно (движок линеен).
4. **Доказательство — живой прогон**, не зелёный `check:core`.
5. **Итеративно — только сборка + `pm2 reload` на текущем сервере; полный деплой в конце** (правило
   `feedback-build-during-iteration-deploy-at-end`).
6. **Каждая веха — отдельный шаг** (`new-step-N`), закрывается по регламенту.

## 3а. УТВЕРЖДЁННАЯ ДОКТРИНА (владелец, 2026-07-29) — «узловые навыки» и федеративное знание

**Термин: Fractera Node Skill (узловой навык)** — нативная функция платформы для срединного узла
(файл в `_lib/nodes/` + скрытый узел в замороженном ядре). НЕ путать с `capability.type="skill"`
(внешний агентский навык). Библиотека узловых навыков = зерно L3-маркетплейса.

**Асимметрия краёв и середины (фундамент):** каналы входа/выхода конечны → закрываются инвентарём
узлов. Логика середины бесконечна (миллионы вариантов) → закрывается ДВУМЯ ярусами знания:

| Ярус | Что | Как модель узнаёт | Размер |
|---|---|---|---|
| 1. Замороженное ядро | курируемые платформенные навыки, скрытые узлы шаблона | дайджест закона, всегда в контексте | десятки |
| 2. Векторный корпус | ВСЕ построенные срединные узлы всего флота | семантический поиск → кандидаты → оценка | неограничен |

**Закон трёх исходов (отказ невыразим):** функция `transform`-узла — это либо (а) навык из библиотеки,
либо (б) свой код в `_lib/nodes/`, либо (в) `capability: needed` + Warning владельцу. Ответ «наша
автоматизация это не может» ГРАММАТИЧЕСКИ НЕ СУЩЕСТВУЕТ — как незаконное ребро.

**Петля роста:** запрос → поиск в корпусе → оценка кандидатов (использовать как есть / адаптировать /
написать заново) → новый узел описывается по стандарту и инжестится обратно. Прецедент механики —
шаг 258 («reuse before build» для целых автоматизаций, `lib/automation-catalog.ts`).

**Правило промоушена:** платформенная способность (склады, ИИ, гео, время) → поднимается в замороженный
стартер скрытым узлом; специфика одного бизнеса → остаётся кодом своей автоматизации.

**Паттерн «исполнение локально — знание федеративно»** (запечатлевается как порты):
1. **Чтение** — при разработке агент спрашивает ЦЕНТРАЛЬНОЕ хранилище знаний Fractera (dev-time,
   мягкий слой, fail-silent); недоступно → фолбэк на ярус 1, разработка не умирает.
2. **Материализация КОПИЕЙ** — выбранный навык копируется внутрь папки автоматизации; импортированный
   код получает статус `candidate` и обязан быть доказан живьём локально до `proven` (supply-chain-гейт).
3. **Взнос** — доказанный узел возвращается в корпус дескриптором+кодом; гейт приватности — флаг
   публичности паспорта; имена `envKeys` идут, значения — никогда.
Локальный LightRAG НЕ заменяется: у него другая работа (runtime-память владельца, твёрдый слой).
Runtime НИКОГДА не зависит от центра.

**Двухуровневый поиск:** рождение автоматизации → искать похожую АВТОМАТИЗАЦИЮ (векторная запись из
`passport.howItWorks` — так задумано схемой); разрыв в середине → искать УЗЕЛ.

**Единица узлового корпуса — денормализованный «паспорт узла»** (порождаемый артефакт, закон 2):
поля узла (`function`, `description`, `info`, `envKeys`) + кейсы, которым служит («зачем») + окружение
в графе («где стоит») + строки `howItWorks` родителя + провенанс-фасеты (`unit=node`, адрес родителя,
cuid узла — паттерн маркеров 258/260).

**Два аддитивных поля схемы (утверждены):**
- `serves: [cuid кейса, …]` у узла — ради какого сценария существует (v1-прецедент: колонка `actions`);
- `lineage` у узла — постоянный id паттерна, ПУТЕШЕСТВУЕТ С КОПИЕЙ (локальный cuid = идентичность
  экземпляра; lineage = идентичность паттерна). Без lineage флотовая агрегация невозможна.

**Телеметрия — третий столп** (дескриптор=что; провенанс=откуда; телеметрия=чем доказано):
- Источник — локальный журнал прогонов `runs.jsonl` (уже пишется движком, пер-узловые статусы).
- Метрика = **распространённость + успешность**, НЕ сырой счётчик: число РАЗНЫХ серверов → доля
  успешных прогонов → активные дни → валовый объём (по убыванию силы; cron накручивает только валовый).
- Доставка — фоновый fail-silent push агрегатов по lineage (раз в сутки); НИКОГДА в пути прогона;
  только числа, ни байта payload; opt-out.
- Ранжирование — на стороне корпуса; поиск возвращает кандидатов со статистикой; `attempts[]` дополняет
  сигналом выбора. Вместе = обучающий актив Fractera.

## 4. Дорожная карта дозревания v2 (вехи = шаги разработки)

Порядок — по зависимостям и ценности. Каждая веха самостоятельна и оставляет v2 работоспособной.

### Веха 1 — рантайм-способность ИИ (`capability` на `transform`)
**Что:** узел-`transform`, чья функция зовёт выбранную в `passport.ai` модель через общий ключ (`OPENAI`/
`ANTHROPIC` из `api/env`) и кладёт результат в контекст (`ctx.summary`). Оформить как `capability`
(`needed→bound`), а не хардкод — это фундамент для сводки и разбора даты.
**Зачем:** save и remind требуют сводки; сегодня ни один узел не думает моделью.
**Объём:** средний. Аддитивно; трогает `_lib/` рантайма, не ломает существующее.

### Веха 2 — чтение памяти (recall) — единственный настоящий новый механизм
**Что:** `_lib/memory.ts` получает `recallFacts(query)` (POST `/api/rag/query` mode=hybrid, тот же
провенанс-контракт, что у записи); новый `transform`-узел «спросить память» кладёт `ctx.answer`; развозка
идёт обычным `deliver-user-telegram-chat`.
**Зачем:** без этого recall невозможен вовсе — память v2 только пишет.
**Объём:** средний. Это ЕДИНСТВЕННОЕ подлинно новое расширение способностей; всё прочее — аддитивы.
**Развилка владельца:** подтвердить, что чтение памяти становится штатной способностью v2 (а не осталось
за границей продукта). До подтверждения — фиксировать как `capability: needed` с warning.

### Веха 3 — дозревание доставки по наступлению (remind end-to-end)
**Что:** (а) `deliverDue` (в `_lib/components/calendar/deliver.ts`) получает канал `user-telegram-chat`
(доставка в личный чат, идемпотентность `deliveredAt` уже есть); (б) `deliver-calendar` уважает
установленное серединой время `ctx.when` вместо «времени захвата»; (в) `transform` разбора даты из
свободного текста (на способности Вехи 1; нет даты → честный ответ «когда?»).
**Зачем:** remind — это отложенный push; сегодня доставка не доходит до личного чата и игнорирует дату.
**Объём:** малый-средний, чисто аддитивный.

### Веха 4 — конвенция группы: сам-гейт по hook-фразе (без нового примитива)
**Что:** описать и оснастить паттерн «группа автоматизаций, каждая слушает тот же личный чат и в своём
`transform` проверяет свою триггер-фразу; чужая фраза → штатная остановка (`null`/throw)». Возможен
крошечный общий помощник «моя ли фраза». Роутер-вид НЕ добавляем (осознанный закон v2).
**Зачем:** так три действия сосуществуют в одном чате без запрещённого N-way роутера.
**Объём:** малый; в основном документирование + маленький helper.

### Веха 2а — НОВАЯ (утв. 2026-07-29): «архитектура срединных узлов» — федеративный корпус узловых навыков
**Что:** спроектировать и построить одним контрактом (порознь разойдутся):
(а) схема дескриптора «паспорт узла» (порождаемый из ядра, состав — §3а) + генератор при взносе;
(б) аддитивные поля схемы: `serves` (узел→кейсы) и `lineage` (id паттерна, едет с копией);
(в) центральное хранилище знаний v0 (Fractera-hosted, LightRAG-подобный сервис + тонкая дверь;
    адрес/ключ новым серверам доставляет L1 через env) — чтение fail-silent, взнос с гейтом приватности;
(г) телеметрия: агрегатор `runs.jsonl` по lineage + фоновый push + join статистики при поиске.
**Зачем:** ярус 2 знания — сетевой эффект флота; без него корпус каждого сервера вечно пуст.
**Порядок:** после Вех 1–3 (ярус 1 не зависит от центра ни байтом); проектирование дескриптора — раньше,
чтобы навыки ядра рождались уже с lineage.

### Веха 5 — приёмка: собрать telegram-notes группой в v2 и доказать живьём
**Что:** кейсы-первыми (шаг 231, ревью-гейт) → группа `save-note` (Вехи 1) + `remind-me` (Вехи 1+3) +
`recall` (Веха 2) → раскрыть узлы через `api/patch op:"visibility"` (ключи через `api/env`) → живой прогон
каждой в Telegram. Паритет подтверждён → снять v1 `personal/telegram-notes`.
**Зачем:** прохождение группы = формальное доказательство, что v2 дозрела до планки прототипа.
**Объём:** сборочный; зависит от Вех 1–4.

## 5. Что уже готово в v2 (не строить заново)
- Приём/нормализация Telegram: `receive-user-telegram-chat`, `receive-telegram-bot` → общий `Message`.

- Запись строки/БД: `deliver-database`, `_lib/rows.ts`.
- Доставка в Telegram: `deliver-user-telegram-chat`, `deliver-telegram-bot`.
- Планировщик наступления: `api/calendar-tick` + `deliverDue` (идемпотентность `deliveredAt`).
- Выбор модели: `passport.ai` + `api/ai-models` (живой список моделей).
- Механизм объявления нужды во внешнем инструменте: `capability` (`needed→candidate→bound→proven`) + `attempts[]`.

## 6. Известные ограничения (страховка следующей сессии)
- Память v2 = только запись (`_lib/memory.ts`), пока не добавлен `recallFacts` (Веха 2).
- Середина = `transform` + `condition-success/failure`; движок линеен, first-throw-stops. N-way роутинг = группа.
- `deliverDue` каналы: `telegram-bot`, `email`, `external-automation` — без `user-telegram-chat` (Веха 3).
- `deliver-calendar` ставит время = момент захвата (Веха 3).
- Ни один узел пока не зовёт модель — сводка/разбор даты = Веха 1.
- Закон 0/1 (самодостаточность): рантайм не тянет `@/lib/*`. Закон 3: паттерны v1 — только с разрешения.
- Кейсы-первыми + ревью-гейт (шаг 231) и живой прогон (не `check:core`) — обязательны.

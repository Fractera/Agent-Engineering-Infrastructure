# CLASS `self-describe` — a question about the automation itself

> **Law of instructions: ENGLISH, COMPACT, one fact one home.** Its reader is a model that must read the core too, so every line here is paid on every session. Prune before you append; never restate what another instruction already says — link to it by name.

**Where the answer lives:** in the passport. **Routes to:** an output, bypassing the middle entirely.

«What page do you have?», «where can I see this?» — the answer needs no store, no external tool and no
key, because the automation already knows it about itself.

## Why this class proves the layer

In the three-layer law such a route was IMPOSSIBLE to express: an edge from a door to an output did not
exist, so the answer had to be smuggled inside some middle node or, worse, inside the delivery node. The
first thing the intent layer bought us is the right to answer without pretending to do work.

## How it recognizes

Deterministically, from a short closed list of forms. The set of ways to ask an automation about itself is
finite, so a model here would add cost and a failure mode without adding reach.

## What it must never do

- **Never invent an address.** An empty `passport.publicUrl` means «not assigned yet», and that is what it
  says. A plausible-looking link is worse than no link: the owner will follow it.
- **Never expand into a general description of capabilities.** «What can you do» is a different question;
  answering it from a hand-written list turns the class into documentation that rots.
- **Never touch a store to answer.** If an answer needs a store, it is not this class.

## Reuse

Domain-neutral, and one of the two classes worth revealing first in any new automation: it gives the owner
something really working to see on the very first run.

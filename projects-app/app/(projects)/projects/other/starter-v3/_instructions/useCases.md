# USE CASES — what makes THIS automation different, in the owner's own words

> **Law of instructions: ENGLISH, COMPACT, one fact one home.** Its reader is a model that must read the core too, so every line here is paid on every session. Prune before you append; never restate what another instruction already says — link to it by name.

A case is one scenario the owner wants to live: what happens, when, and what he sees at the end. The SET
of cases must be enough, on its own, to build what is SPECIFIC to this automation. Read them before you
look at a single node.

## 🔒 A CASE CARRIES ONLY THE DISTINCTIVE — a universal guarantee is never a case

A case says how THIS automation differs from every other one: studying books · sports training · losing
weight · finding business partners. It is a subject area and this owner's scenario, written out in
detail. **Cases are the only thing that changes from automation to automation.**

Anything true of EVERY automation regardless of its purpose is LAW, and law lives in the schema, the
instructions and the law digest. It does not come into being because someone wrote a case, and it does
not disappear when a case is removed.

**THE TEST — apply it before you write any case:**

> Remove the description. If the behaviour still CANNOT be violated, it is LAW and has no place in the
> cases. If the behaviour disappears without the description, it is a CASE — and it must be detailed.

**Why this is safety, not taste.** A case is edited by the owner of one automation. Put a universal
guarantee into a case and you make it deletable: the owner removes "answers honestly" and silently loses
a guarantee the platform is obliged to hold. Law cannot be deleted, because you trip over it — the schema
refuses, the module fails to load, the engine fails the run. **A case is a REQUEST; a law is a
GUARANTEE.** A request is read by a model, and a model may not read it. A law is not read at all.

Real precedent (step 311.9): three cases were written — "answers honestly", "captures and fans out",
"says where it is published" — and every one of them was already law. Three second homes for one fact.

## No case, no node — and what that does NOT cover

The rule governs what you BUILD: middle nodes, and the decision of which doors to reveal. A node nobody
asked for is waste, however clever.

It does NOT govern the frozen inventory that stands by law — the request classes of the intent layer, the
channel doors, the connectors, the toast. Those exist in every automation whether or not any case names
them. Consequently `serves` is carried only by nodes born from the owner's scenario; a node standing by
law never carries it, and an empty `serves` there is the truth, not an omission.

## The frozen template ships with NO cases

A template has no purpose yet — the owner gives it one, and a newborn clone with an empty set is what
opens the Quiz. The schema enforces it: `lifecycle: "frozen-template"` carrying a case is refused.

## The rules you work by

- YOU DO NOT INVENT CASES. Not enough to build from → a warning on `useCases` naming the question you
  would ask the owner, and stop there.
- A CONFLICT lives on the SET, not on either case: say which two collide and what makes them irreconcilable.
- `number` IS HOW THE OWNER SPEAKS ("in case 02, change…"). Unique; the core issues it on append.
- `status` WALKS ONE WAY: `new` → `in-development` → `in-use`. Move it as you actually work; `in-use`
  means you proved it on a real run.
- REFINE A CASE'S TEXT only to make the owner's own meaning precise — never to narrow it to what you
  managed to build. Built less than the case asks → the case stays, the shortfall becomes a warning.
- AN INCOMING REQUIREMENT LANDS HERE FIRST (any development channel: the send-task box, a `rawRequest`,
  any request field). Reconcile it with the SET — append, rework, or warn — and only THEN touch nodes and
  edges. A graph changed without its case is unlawful drift.
- THE PANEL AND THE QUIZ ARE NOT YOURS TO CODE (AGENTS.md §0a). You change `useCases.cases` through
  `api/patch`; the view is platform-owned and identical in every account.
- THE OWNER SIGNS THE SET. `reviewedSignature` records the set he last confirmed; any add/edit/delete
  changes the signature, and the gate asks him to read and confirm again.

## Their weight

A real project without a single case is unlawful — the core refuses it. An automation is defined by what
it is FOR, not by the nodes that happen to exist inside it.
